# Operations and detection

*[Leia em português](operacao.md)*

## What the API emits

| Signal | Where | Content |
|---|---|---|
| Log | stdout, one JSON per line (`LOG_TO_FILE=true` also writes to files) | `correlationId`, `traceId`, route without query, status, duration. Password, token, cookie, email and database parameters never, at any depth |
| Metric | its own port (`METRICS_PORT`, 9464), off the edge | RED per route and security events by reason. Labels only from a closed list |
| Trace | OTLP, when `OTEL_EXPORTER_OTLP_ENDPOINT` is set | HTTP, Express, Postgres (SQL with placeholders) and Redis (command only). No URL query and no IP |
| Audit trail | `audit_logs` table | who, what, when, from where |

The response `X-Request-ID` is the log `correlationId` and the error body `requestId`. It is always
generated by the server; whatever the client sends goes to `clientRequestId`.

`backend/tests/smoke/telemetria.cjs` starts the compiled API in production mode and checks all of
this, including that nothing sensitive reaches logs or traces.

## Service objectives

- 99.5% of responses without 5xx over 30 days, health probes excluded.
- Login p95 up to 1.5 s. bcrypt at cost 12 takes about 200 ms on purpose.

## Probes

| Route | Answers | For |
|---|---|---|
| `/health/live` | the process is up | container restart |
| `/health/ready` | the database answers within 2 s | load balancer |
| `/health` | database and cache state | people |

`live` and `ready` are outside the rate limit; `ready` keeps its result for 2 s. Without Redis the
API degrades and stays ready: revocation is still checked in the database.

## Alerts

Rules are in [`observabilidade/regras.yml`](../observabilidade/regras.yml), tested by
`regras.teste.yml`. Detection rules carry the MITRE ATT&CK technique. Annotations link to the
Portuguese runbook.

| Alert | Technique | What to do |
|---|---|---|
| OrcamentoDeErroQueimando | | Find the route in `authcore_http_requests_total`, then follow `traceId` from the error log. Client errors are not here: large body is 413, broken JSON is 400 |
| LoginLento | | Only login slow is CPU (bcrypt): check for password spraying. Everything slow is the database: look at `pg.query` spans |
| ApiForaDoAr | | Check `/health/live` and the last process exit in the log |
| RefreshTokenReutilizado | T1550.001 | Sessions are already revoked. Compare IP and browser with the previous login in the trail: different means theft, same means a client renewing twice |
| PulverizacaoDeSenha | T1110.003 | Trail by IP: many users per IP is spraying. Block at the edge. An `auth.login` from the same IP is a compromised account |
| EnumeracaoDeContas | T1589.002 | Answers and timing are equal, so it should not pay off; block the IP anyway, it prepares the next attack |
| AtaqueAoSegundoFator | T1111 | Only who has the password gets here. `totp_replay` is a code read in real time (proxy phishing): treat the password as leaked and offer passkeys |
| AcessoNegadoEmMassa | T1078 | A legitimate account trying routes above its role: taken over or curious |
| TrilhaDeAuditoriaFalhando | T1562.008 | Events still reach metrics and logs. Check space and `INSERT` permission on `audit_logs`, and any unplanned permission change |

## Privacy

IP and browser stay in logs and in the audit trail to investigate incidents (legitimate interest,
LGPD art. 7, IX) and do not reach metrics or traces.
